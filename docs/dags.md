# DAGs: the pipelines

Twenty-three DAG packages and one library, all in `airflow/dags/`. Which source each one reads:
[sources](sources.md). Every DAG starts paused (Airflow's default, `dags_are_paused_at_creation`);
unpausing it in Airflow is the only switch.

| package | DAG id | schedule | what it does |
|---|---|---|---|
| `pipeline_coordinator/` | `pipeline_coordinator` | triggered | the ONLY thing that decides which observation wins a field |
| `website_discovery/` | `website_discovery` | `@hourly`, a full batch starts the next | guesses domains, reads the Impressum, keeps only websites the page proves are the company's (`confidence.identifies_company`). Rechecks after `WEBSITE_DISCOVERY_RECHECK_DAYS` (90). |
| `wikidata/` | `wikidata` | `@daily`, a full batch starts the next | websites Wikidata lists for Berlin organisations (one SPARQL query a day, CC0), matched by register number and name or a unique name of a company that is not dissolved, each verified like a guessed domain (`pipeline.verify_proposed`); only a page that identifies the company is shown |
| `common_crawl/` | `common_crawl` | `@weekly`, a full batch starts the next | Impressum pages of the newest Common Crawl that name a Berlin register number: 300 `.de` index blocks a run, position in `pipeline_state`; each host proposed to the company whose register identifier it names and verified like a guessed domain (`enrichment.proposals`). Each run also logs how many pages name only HRA/HRB numbers we do not have, and how many of those name one above the OffeneRegister range (#99), to decide whether such pages should create companies. The counts are per run: a page seen in two runs counts twice |
| `website_contacts/` | `website_contacts` | triggered | every email on the Impressum of the company's proven website, each with a kind (`role` 0.6, `person` 0.4, `other_domain` 0.2), and its phone (source `impressum_contacts`). A read replaces the company's earlier contacts; a company read under an older rule is read again. Stored, never resolved; emails are listed on the company page through `v_company_emails` (`V6__company_emails.sql`), phones never shown. A failed read is retried, 3 times at most |
| `impressum_address/` | `impressum_address` | `@daily` | the company's current address from the Impressum of its website, only when the page names the company's register number and no other; the page's first address, only when it is in Berlin (source `impressum`, #141). Each company read once; a failed read is retried, 3 times at most |
| `website_keywords/` | `website_keywords` | triggered | keywords from meta tags and services/products headings; generic ones measured out over all companies read; publishes `activity_keywords` once 500 companies are read; also the homepage's own description as `activity_description` (#152, `enrichment.site_description`); retried 3 times at most |
| `structured_data/` | `structured_data` | `@weekly` | the founding date or year the company's own website states in its schema.org JSON-LD, read from the stored pages of its published website only (no downloads), only from a node that names the company. The year becomes `founding_year` (V6), a full date also `established_at`; a year alone never becomes 1 January; pages disagreeing on the year write nothing |
| `technology_field/` | `technology_field` | `@daily`, then batch after batch while batches come back full | Berlin's Technologiefeld from the keywords on the homepage and services pages (`branch_classifier`); keywords weighed over all companies read, so every run classifies them all again; writes once 500 companies are read; a value a company loses drops to confidence 0; retried 3 times at most. Where no keyword fired, a promoted text classifier may fill the field (`decided_by = textcat`) |
| | `technology_field_train` | `@weekly` | trains the text classifier on the keywords' answers and the app's votes, from the corpus; promotes it only when it is right often enough on held-out companies people judged and the keywords left empty (none yet) |
| `purpose_field/` | `purpose_field` | `@daily` | column 3 (#178): the field the register's business purpose names, by keywords (`purpose_branch`), from each company's published `business_purpose` (today only `openregister` has one); no downloads, no model; weighed over all purposes over 40 characters, so every run classifies them all again; writes once 500 such purposes exist; a shorter purpose gets only `purpose_field_withheld`, which nothing publishes; a value a company loses drops to confidence 0; source `purpose_classifier` |
| `wz_estimate/` | `wz_estimate` | `@weekly` | "WZ (geschätzt)" (#158): trains a text classifier over the WZ divisions on Claude's `wz_division` labels from `llm_labels`, overridden by the app's votes on `wz_division_estimated`; judged on a held-out fifth by Claude's labels until 30 held-out companies have a person's label, then by people only; then the promoted model writes `wz_division_estimated` (source `wz_textcat`, confidence = its probability) for every company whose published website was read. Never the official `wz_code`. Nothing written until a model is promoted |
| `review_round/` | `review_round` | **by hand only, never scheduled** | draws one review round (#153, [review-queue](review-queue.md)) from the trigger form: field, kind (`shown`/`refused`/`gap`), source, size (at most 1,000), mode (`measure` random, `teach` closest to the bar), version, title. Writes only `review_rounds` and `review_tasks`; never retried, since a retry would draw a second round |
| `llm_labels/` | `llm_labels` | **by hand only, never scheduled** | Technologiefeld teacher labels from the Claude API (#87), with an estimated WZ division in the same answer (#140), for companies whose published website the keywords left empty (`no_keyword`), and once those are all labelled, companies the keywords gave a field (`assigned`, for the WZ model #158; `keyword_outcome` in the record): services pages and homepage from the corpus, never the Impressum, names (spaCy `PER`), emails and phones replaced first. One Message Batch per run, at most `LLM_MAX_COMPANIES_PER_RUN` (500); no new batch once `LLM_MONTHLY_TOKENS` (10 million) are used this month. Labels go into source records of `llm_technology_field` with model and prompt version, never into observations, so never into the app. Key `ANTHROPIC_API_KEY`, an Airflow variable. Checked by hand: `scripts/llm_labels_sample.py` |
| `gleif/` | `gleif` | `@daily` | Berlin companies with an LEI from GLEIF's open data: the full file on the first run, then the weekly change file (up to 5 days since the last good run), the monthly one (up to 28), else the full file again. Only Charlottenburg entries (`RA000217`) with a Berlin address. Linked like register announcements (`enrichment.register_match`); active companies we lack are created, inactive ones only update a company holding their register number (never matched by name). Writes name, legal form, address, postcode, city, status (`ACTIVE` active, `INACTIVE` dissolved) and the legal entity's creation date (`established_at`, its year `founding_year`; #137) and, for an inactive entity that went into another, the successor's LEI (`successor_lei`, shown through `v_company_successor`; #167), dated by GLEIF's last update, and the LEI as an identifier. A name differing only in case or punctuation is not written |
| `register_announcements/` | `register_announcements` | `@weekly` | Berlin's register announcements of the last 8 weeks from handelsregister.de (2 requests, the result list only, never a detail page). Linked by register number, then name and city (never to a deleted company); unknown companies are created. Publishes the latest as `register_announcement`, a hint next to `register_status`, never a change of it |
| `openregister/` | `openregister` | **by hand only, never scheduled** | Berlin companies from OpenRegister's company search: those incorporated since 2019 first, then, with the searches a run has left, older ones one founding year at a time (2018, 2017, … down to 1900; #143), and for those the year of that pass as `founding_year` (#137; the search returns no date, the year comes from the filter); once a backlog page has mostly HRB numbers above 203,000 (the search seems to ignore its upper date bound), `years_untrusted` is set in `pipeline_state` (openregister / search) and no later backlog page writes a year until a person deletes that key (key `OPENREGISTER_API_KEY`, an Airflow variable), at most `OPENREGISTER_MAX_SEARCHES` (10) searches of 10 credits per run, stopping when the balance runs low; the position is kept in `pipeline_state`. Written like `gleif` (`enrichment.register_match.write_entry`), with the business purpose. No retries: a retry would spend credits again. Storing and regular retrieval are not yet confirmed by the operators |
| `web_search/` | `web_search` | **by hand only, never scheduled** | websites discovery missed, from the Brave Search API (#92): up to 100 active companies without a website per run (sole traders left out), query "name" Berlin, up to 20 results per query, the first 3 hosts that carry the company's name proposed and verified like a Common Crawl proposal. Needs the Airflow variable `BRAVE_SEARCH_API_KEY`. Price and whether results may be stored are not checked, so a person starts every run |
| `handelsregister_lookup/` | `handelsregister_lookup` | **by hand only, never scheduled** | name, seat and status of up to 50 companies with a website from handelsregister.de, one search each by register number, 72 s apart (the portal allows 60 an hour). The portal's Nutzungsordnung forbids systematic retrievals that keep a partial register current (Ziffer 3); built anyway on the developer's decision of 2026-10-31, so a person starts every run. Result list only, never a document |
| `wirtschaftsatlas/` | `wirtschaftsatlas` | **by hand only, never scheduled** | companies with a website from Berlin Partner's Wirtschaftsatlas (about 57 GeoJSON layers, 2 s apart), matched by name key and postcode, else a unique name of a company that is not dissolved; each website verified like a Wikidata proposal (`enrichment.proposals`), up to 500 a run. The atlas offers no licence; its Impressum asks for Berlin Partner's prior consent. Built anyway on the developer's decision of 2026-11-04 while Berlin Partner is asked (#105), so a person starts every run. The layers (AI, FinTech, ...) are kept in the record; a company whose mapped layers name one Technologiefeld gets it at 0.56, below the keywords (#148) |
| `register_crosslink/` | `register_crosslink` | `@weekly` | websites from register numbers discovery found on another company's guessed site (#112): each (host, one of our companies' register entries) is proposed to that company and verified like a Common Crawl proposal; a host naming more than 2 of our companies proposes nothing. Local, 2026-11-04: 6,048 proposals, 7 of the first 100 proven (all by the own register number), 3 of them new |
| `ba_jobsuche/` | `ba_jobsuche` | **by hand only, never scheduled** | Berlin employers with open job ads from the Federal Employment Agency's job search (#106): every Berlin ad of the list view, grouped by employer, matched to a company by name and postcode (`enrichment.name_match`); only matches are stored (name, Berlin postcodes, number of ads), no observations yet. The portal's terms forbid reading it for data collection (2a (3)); built and run by hand on the developer's decision of 2026-11-04 |
| `berlin_zuwendungen/` | `berlin_zuwendungen` | `@monthly` | Land Berlin grants to HRA/HRB recipients into `company_fundings`, linked by register number. Then `create_companies`: a recipient's register number we do not have is linked by a unique live name in the same city, or, above the OffeneRegister snapshot's range, created as a company (name, legal form, city; no register status); triggers the coordinator (#103) |
| `cordis/` | `cordis` | `@monthly` | EU research grants (Horizon Europe, Horizon 2020) of private Berlin companies from CORDIS's CSV files into `company_fundings`, one row per participation, linked by a name key unique in its city like the Förderkatalog; never creates a company (no register number) |
| `foerderkatalog/` | `foerderkatalog` | `@monthly` | every Berlin grant from the Förderkatalog des Bundes into `company_fundings` |
| `feedback_observations/` | `feedback_observations` | `@hourly` | people's corrections from the app as observations of `user_feedback` (priority 50); shown once two people agree, never who. Triggers the coordinator only when something changed |
| `manager_ner/` | `manager_ner_extract` | triggered | spaCy reads the Impressum and writes Geschäftsführer names (source `spacy_ner`) |
| | `manager_ner_train` | `@weekly` | turns the app's votes into training data, plus register officers found on the Impressum as extra labels (#58); promotes a model only if it beats the current one on a held-out fifth people voted on |
| `enrichment/` | — | — | the library: URL patterns, Impressum regex, confidence, classification. `__init__.py` is the map |

Grants are linked to companies by `refresh_company_funding_links()` after a load.

- **observation**: one claim about one field of one company, from one source, with a confidence.
  Sources write observations and nothing else.
- **canonical**: the observation that won a field, what the app shows. Only `pipeline_coordinator`
  decides, by source priority first, then confidence.

Shared code:

- `source_enrichment_common.py`: the database helpers (`PG_DSN`, `ensure_source`,
  `upsert_source_record`, `insert_text_observation`, batch queries, `DISCOVERY_ACTIVE_ONLY`).
  `insert_text_observation`'s `ON CONFLICT ... WHERE` repeats the partial index predicate of the
  upsert key verbatim: widen one, widen the other, same commit.
- `pipeline_task.py`: build every task with `pipeline_task(task_id, run)`; it runs in Airflow's
  Python locally and as a pod on the hub ([release](release.md)). A failed task runs again twice,
  10 minutes apart: on play a 503 from foerderportal.bund.de and a Wikidata timeout each failed a
  run that would otherwise wait for the next schedule (#86). `retries=0` turns that off;
  `handelsregister_lookup` uses it, because a retry would spend the portal's request limit again.
  `run` may live in any module of its package (`technology_field.train:run_train`); a unit test
  resolves every task of every DAG file the way a pod does.
- Import modules **by package name** (`from enrichment.confidence import ...`), never as a bare
  module after a `sys.path` insert: two same-named files would get each other's.

Schema changes belong in `db/migrations/`.
